# Browser UI を chromatic-rail へ移植する

状態: 採用

2026-09-22に、uiux-numaのIssue #15で比較したBrowser UI案から、利用者が選択した`chromatic-rail`を本体へ移植した。

## 背景

従来のBrowser UIはheader、編集対象、タブ、本文、status barを縦に積んでいた。
主要画面では編集対象とタブが本文の上に横幅を使い、workspace操作と接続・入出力操作も同じheader行に並んでいた。
保存競合・キュー状態の実装が先に入ったため、既存の状態管理と操作を維持したまま視覚的な階層を変更する必要があった。

## 選択肢

1. 既存の横積み構成を維持する
2. `chromatic-rail`の左レール、主操作header、本文下status barへ移植する
3. 実験案のナビゲーション項目をそのまま本体へ追加する

## 決定

案2を採る。
headerにはbrand、workspace、接続状態、workspaceを開く主操作、テーマを残し、接続・VIL・再読込・backup復元はネイティブの補助メニューへまとめる。
編集対象と対象別タブは左レールへ移し、現在位置は背景、文字、左境界、`aria-current`で示す。
既存のCornix / Macのタブ構成、`EditTargetSelect`の対象モデル、`StatusBar`のApply・保存先・診断導線は変更しない。
狭い画面ではレールを横方向へ切り替え、タブの横スクロールを許可して本文の横幅を確保する。

## 理由

案1は操作の意味を変えないが、本文とナビゲーションの境界が弱く、主要な編集領域の横幅を継続して消費する。
案2は選択対象とタブを一つの編集ナビゲーションとして視認でき、保存状態とApplyを本文下へ残せる。
案3は実験側の5項目を現在の対象モデルへ持ち込むため、Mac対象選択と既存タブの責務を重複させる。
実験の見た目は再利用するが、実アプリにない遷移や操作は追加しない。

## 影響

headerの補助操作は常時表示ではなくなったが、操作自体とdisabled条件は維持した。
CSSは既存のsemantic tokenとprimitiveを使い、light / dark themeの両方でレールとactive状態を表現する。
実機への書き込みやOS設定の変更はこの移植では行わない。

## 却下理由

既存の横積み構成はIssue #15の採用案ではないため採らなかった。
実験案のMac専用トップレベルtabは実アプリの編集対象selectと責務が重なるため採らなかった。
