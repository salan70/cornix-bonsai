# 2026-08-19 D-002 `keymap.yaml` schemaを決める

対象Issue: #7 `[D-002] keymap.yaml schemaを決める`

## 調査方法

- ADR 0001・0002・0006・0007が`keymap.yaml`へ送っていた制約を洗い出した
- 「何を載せるか」と「どう並べるか」を分けて扱い、前者を先に決めた
- 並べ方の候補3案をSpike（`spikes/d-002-keymap-yaml/`）で代表fixtureへ当て、
  全体行数と変更時のdiff行数を実測した
- 採用案を`src/core/keymap-yaml/`へ実装し、往復をtestで押さえた

## Fact

- ADR 0006は「状態は`VilDocument`ただ1つ、意味表現は保存も比較の正ともしない」と決めている。
  `keymap.yaml`をSemantic Model側の射影にすると、この決定が崩れる
- `edge-cases.vil`にはhex表記のkeycode`"0x1234"`がある。**YAMLで引用しないと整数`4660`として
  読まれる。** keycodeの引用は好みではなく必要条件
- `-1`（物理キー無し）と`KC_NO`（キーはあるが未割り当て）は別物で、型でも別（`VilKeyEntry`）
- 候補3案の実測（`baseline.vil`、8 layer × 8 row × 7 col）

  | 案  | 全体行数 | 1キー変更のdiff行数 | layer追加のdiff行数 |
  | --- | -------- | ------------------- | ------------------- |
  | A   | 659      | 2                   | 65                  |
  | B   | 99       | 2                   | 9                   |
  | C   | 569      | 2                   | 56                  |

- **1キー変更のdiffは3案とも2行**で、ここでは案の差が出ない
- `macro`・`key_override`・`alt_repeat_key`・未知fieldは、ADR 0001が「解釈せず持ち回る」と
  決めている対象。YAMLの構造へ展開すると解釈したことになる

## Inference

- 1キー変更のdiff行数で差がつかない以上、Git diffの読みやすさを決めるのは**全体行数と、
  hunkの中に格子が残るか**である。案Bだけがrowを1行に保つ
- desired stateはApplyの入力なので、読み違えのコストが読めないコストより高い。
  したがってparserは書き方の揺れを吸収する方向ではなく、部分集合の外を落とす方向へ倒す
- 部分集合に限ればflow sequence 1行はそのまま`JSON.parse`へ通せる。
  **YAML libraryの依存追加はこのschemaでは不要**という結論になった

## Spike結果

`spikes/d-002-keymap-yaml/self-check.mjs`（実機もbrowserも不要）は全チェック通過。

- 3案の全体行数とdiff行数を実測した（上表）
- 案Bのlayer追加は「row数 + 見出し1行」の追加だけで、既存layerの行が1行も動かない
- hex表記のkeycodeが引用されることを確認した

## Decision

ADR `docs/decisions/0009-keymap-yaml-schema.md`（状態: 採用）に記録した。

`keymap.yaml`は`VilDocument`の**可逆な射影**であり、`KeymapView`のmaterializeではない。
並べ方は案B（row 1本 = 1行のflow sequence）。keycodeは必ず引用し、`-1`は数値のまま置く。
解釈しないfieldは`raw.json`のblock scalarへJSONのまま入れる。
parserは汎用YAMLではなくemitterの部分集合だけを受け付ける。

実装は`src/core/keymap-yaml/`、仕様は`docs/specs/keymap-yaml.md`。
test 11件を追加した（合計53件）。往復が成立することを示す中核は以下。

- `baseline.vil`と`edge-cases.vil`の両方が`keymap.yaml`経由で`VilDocument`へ戻る
- `keymap.yaml`を経由しても`.vil`のbyte一致round-tripが壊れない
  → `keymap.yaml`が第2のモデルでないことの検証
- commentを足しても読み取り結果が変わらない → 注記が状態でないことの検証
- 1キーの変更でdiffが1行になる → 採用理由を契約としてtestに置いた
- block styleで書き直したrow、引用の無い`uid`、arity違反の`tapDance`はいずれもerrorになる
  → 部分集合の外を黙って読み違えない

## Open Question

- **`.vil`に無いユーザー情報（layer名・キーの説明）を持てない。** 持たせるには
  ADR 0006の「状態はraw 1つ」をraw + sidecarへ広げる判断が要る。v1では載せないと決めたが、
  実際にUIを作った段階で不足が出る可能性がある
- `settings`のqsidが生のまま出るため、この部分は人間に読めない。semanticな設定名への
  対応づけはD-003の範囲
- macroが`raw.json`のJSON塊になるため、macroの編集はYAML上でJSONを触ることになる。
  macroのsemanticな表現は未検討
- 手書きのYAMLがCornix Bonsaiの部分集合から外れると読めない。AIエージェントやCLIが
  編集する運用で、この制約が実際にどれだけ摩擦になるかは未検証
- workspaceへの実際の読み書きはD-004。`keymap.yaml`の置き場所と権限の話はそちら
