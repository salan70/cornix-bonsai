# 2026-08-19 D-005 安全な実機Applyフローを決める

対象Issue: #10 `[D-005] 安全な実機Applyフローを決める`

## 調査方法

- ADR 0005 を読み、結論として確定済みの事項とD-005へ送られた未確定事項を分離した
- ADR 0004 の往復timeoutの初期値と、R-004 / R-005 の実測latencyを突き合わせた
- Applyの状態機械を実機I/Oから切り離した純関数として実装し、
  ADR 0005 が挙げた失敗モードをtestで押さえた
- **実機操作は行っていない。** AGENTS.md の禁止事項どおり、write / flash / reset は実行していない

## Fact

### ADR 0005 で確定済みの事項（D-005で再決定しない）

- writeは単一entry commandに限る。`0x13`と`0x0F`は使わない
- reset系（`0x0A` / `0x0B` / `0x06` / `0x15`）はcommand table自体に載せない
- ackを成功と見なさない。1件writeするごとに同じentryを読み直す
- 再readが一致しても永続化の証明にはならない
- 中断したら未完了の差分を持ち回らず、全readからやり直す
- rollbackはbackupの値を同じ差分write経路で書き戻す操作として定義する
- Apply前の全read backupを必須の前提条件にする

### D-005へ送られていた未確定事項

- 往復timeoutの確定値（ADR 0004 が初期値3000ms、R-004 / R-005 の両ログが「D-005で決める」）
- AI / CLIからのwrite境界を実装上どこで引くか
- 「ackが返ったのだから書けているはず」でdiffを縮めない、をコード上どう保証するか

### 判断材料になった実測（ADR 0005 より）

- read単発 p50 30.0ms / max 512.4ms、write単発 p50 45.0ms / p95 174.7ms（BLE）
- 空き269箇所への連続write中に電源を切ると、ackが返った17件のうち残ったのは16件。
  **ackとflashのズレの幅は1 entry**。残った位置と消えた位置の境界は連続していた

## Spike結果

Spikeは作らず、`src/core/apply/`の実装とtestで確認した。
ADR 0005 の時点で失敗モードは`spikes/r-005-write-failure/`のmockで再現済みのため、
D-005で新たに測る対象が無い。

test 13件を追加した（合計42件）。前提条件が破れないことを示す中核は以下。

- 空のbackupでは`createApplyPlan`が`ApplyPreconditionError`を投げる
  → backupが無ければ計画そのものを作れない
- 状態を進める`recordVerifyResult`が受け取るのは再readの値だけで、ackを表現する型を持たない
  → ackを成功判定に使うコードが書けない
- 中断状態に`plan`も`cursor`も存在しないことをassertしている
  → 「途中まで書けているから残りだけ書けばよい」というコードが書けない
- 許可リストに`0x13` / `0x0F` / `0x0A` / `0x0B`が無いことをassertしている
  → reset系を実装しないことがそのままAI / CLIの境界の実体になる

## Decision

ADR `docs/decisions/0008-apply-flow.md`（状態: 採用）に記録した。

前提条件をフラグやassertionではなく**型と引数**で強制する。中断状態には未完了の差分を
持たせない。往復timeoutは3000msのまま確定する。

## Open Question

- **往復timeoutを3000msから詰められる根拠がまだ無い。** BLEのmax 512.4msの由来
  （connection interval更新 / flash read / OSのscheduling）が未確認で、
  `sequential-storage`のGCがwrite latencyへ与える影響も未測定。両方が埋まれば再検討できる
- ackとflashのズレが常に1 entryかは1回の測定でしか確認していない。
  storage taskの`store_item`所要時間とwrite間隔次第で複数件になりうる（R-005からの持ち越し）。
  ただし今回の設計は「ackを根拠にdiffを縮めない」ため、幅が何件でも結論は変わらない
- USB接続でのwrite再測が未了。R-005 はBLEのみ（R-005からの持ち越し）
- validationのうちどれをApply blockingにするかは未定。severity modelを決めるD-003 の範囲で、
  現状の状態機械はvalidationの結果を引数に取らない。D-003 の後に前提条件として足す
- backup JSONの置き場所はD-004
- 実機との往復を行うadapterは未実装。再送の実装はadapter側の責務で、
  状態機械は再送を区別しない
