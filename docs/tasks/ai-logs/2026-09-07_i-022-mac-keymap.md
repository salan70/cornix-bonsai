# mac-keyboard.yamlとKarabiner generatorの実装

対象Issue: [I-022] #21

## 目的

ADR 0022が決めた「MacBook内蔵キーボードはKarabinerをengineとし、Cornix Bonsaiはdesired stateと
generatorに徹する」を実装へ落とす。判断はD-007（#20、closed）で完了しており、
`spikes/r-006-macos-keyboard/`に動くプロトタイプがある。これを本実装へ移し、CLIから
Karabinerへ適用できる状態にした。

## 判断

- **keycodeの構文層は`classifyKeycode`を単一の定義元にする**（ADR 0023）。ADR 0022と
  Issue #21は`src/core/keycode/table.ts`からpattern解析を切り出し`ResolvedKeycode`へ
  `TG(n)`とmod-tapを足すとしていたが、`src/core/validation/keycode-vocabulary.ts`の
  `classifyKeycode`が`definition`も`capacities`も取らない純関数として同じ構文を
  すでに解いていた。加えてADR 0010が「語彙表を`table.ts`へ置かない」を決めていた。
  そのまま進めると構文解析が4実装目になりADR 0010と逆行するため、方針を変えた。
  結果としてCornix LP側の解釈は一切変わらず、`table.test.ts`の
  「正規化テーブル未実装のkeycodeは表記を保ったまま素通しする」も無傷で通る
- **Browser UIは書き出しまで**にする。ADR 0022は「編集・validation・書き出しまで」と
  書いているが、内蔵キーボードのboard描画とKeycodePicker連携は物理配列定義の新規作成を伴い、
  Issue #21のスコープを大きく超える。編集はエディタで`mac-keyboard.yaml`を直接触る
- **`spikes/r-006-macos-keyboard/`は凍結する。** 1行も変更していない。`self-check.mjs`が
  固定していた契約は`src/core/mac-keymap/generate.test.ts`へ移し、以後は本実装のtestが正。
  `verify-on-macbook.sh`は開発環境の無いMacBookで実機確認するためのものなので、
  埋め込みJSONごとそのまま残した
- **`modified`（`LSFT(KC_1)`）は今回落とさない。** Karabinerでは`to`の`modifiers`で
  表現できるが、Issue #21の要件に無い。「将来の仮想要件に備えたコードを禁止」に従い
  error diagnosticにして、必要になった時点で足す
- **Vial側の`reachability/trapped-layer`はMac側で見ない。** Karabinerではlayer 0の
  manipulatorが変数の状態に関わらず常に効くため、`TG(n)`を置いたキーが上のlayerで
  潰されていない限り出口は必ずある。Vialの閉じ込め判定をそのまま移すと嘘になる
- **`diff`と`verify`は構造で行う。** `karabiner_cli --format-json`が独自整形で
  ファイルを書き換えるため、テキスト比較では毎回「変更あり」になる（D-007で実証済み。
  今回も実配置に対して再確認した）

## 変更

- `docs/decisions/0023-mac-keycode-syntax-source.md`を追加し、Issue #21の本文を更新した
- `src/core/mac-keymap/`を追加した。`types.ts`（`MacKeymapDocument`）、
  `parse.ts` / `serialize.ts`（`mac-keyboard.yaml`）、`key-codes.ts`（Karabinerの
  `key_code`語彙）、`karabiner.ts`（`karabiner.json`の型）、`generate.ts`（展開規則）、
  `validate.ts`（表現可能性・位置・到達性）、`apply.ts`（構造diffと適用計画）
- `src/karabiner/node.ts`を追加した。`karabiner.json`のread、temp + renameでのatomic write、
  `karabiner_cli --lint-complex-modifications`の呼び出し。`src/core/mac-keymap/`は
  filesystemに触らない
- `src/core/validation/reachability.ts`から`analyzeLayerGraph`を純関数として切り出し、
  `analyzeReachability`をその薄いwrapperにした。到達性はkeycodeだけで決まるので、
  matrixを持つdeviceに限る理由が無い
- `DiagnosticSubject`へ`macKey`を足した。位置はKarabinerの`key_code`名で、matrixの
  row / colを持たない。`subjectKey`がexhaustive switchなので追加漏れはコンパイルで止まる
- `KEYCODE_ALIASES`へ`KC_RGHT`を足した。QMKのaliasだが表に無く、Mac側で
  「Karabinerへ落とせない」扱いになっていた
- `WORKSPACE_LAYOUT`へ`macKeymap`を足し、`backupPath`の`.vil`固定を解いた
- `cornix mac generate|diff|apply`を追加した。`keymap.yaml`もdefinitionも要らないため、
  `import vil`と同じく`loadWorkspace`の手前で分岐する
- Browser UIへ`Mac書出`ボタンを足した。errorが1件でもあれば書き出さない。適用はしない
- `fixtures/mac-keyboard/`に`desired.yaml`と`karabiner-baseline.json`を追加した
- `docs/specs/mac-keymap.md`を追加し、`validation.md` / `workspace-cli.md` / `ui.md`を
  更新した。`docs/user-guide/cli.md`へ利用者向けの手順を足した

## 検証

`nix develop -c just typecheck` / `just test`（249件）/ `just lint` / `just docbridge-check`
がすべて通る。`pnpm build`も通る。oxlintのwarningは着手前の10件から9件へ減った（増やしていない）。

実機とKarabinerを使った確認は以下を行った。作業マシン（Mac mini）にKarabiner 15.9.0がある。

- **`key_code`表153件が`karabiner_cli --lint-complex-modifications`を通る。** 全件から
  manipulatorを作って一括で通した。存在しない`key_code`を1件混ぜるとlintが弾くことも確認し、
  lintが名前を実際に検証していることを裏取りした
- **`karabiner_cli`はエラーがあってもexit codeを0で返す。** 判定は出力が`: ok`で
  終わるかどうかで行う。adapterはそう実装した
- **`cornix mac generate`の出力がlintを通る**（`fixtures/mac-keyboard/desired.yaml`から）
- **`cornix mac diff` / `apply`を実`karabiner.json`のコピーに対して実行した。**
  `--karabiner`でコピーを指定している。**実ファイルへは適用していない**（D-007の
  Open Questionが未解決で、作業マシンに内蔵キーボードが無いため）。確認できたこと:
  - `--confirm`無しでは書き込まない。fingerprintが違うと終了コード1で拒否する
  - backupが元ファイルとbyte単位で一致する
  - `Default profile`が無変更で、`selected`も保たれる
  - 再適用しても構造diffがゼロになる
  - `karabiner_cli --format-json`を通すとテキストは変わるが、構造diffはゼロのまま
- **Spikeが凍結されている。** `self-check.mjs`の25件が変更前と同じく全件通り、
  `git diff`にspikeのコード変更が出ない
- **Browser UI**は`just dev`で起動し、`Mac書出`ボタンがheaderへ並び、workspace未選択時に
  無効化され、consoleにエラーが出ないことを確認した。File System Access APIのdirectory
  pickerは人の操作が要るため、書き出しの実行は`generateBrowserKarabiner`のunit testで
  代替している
